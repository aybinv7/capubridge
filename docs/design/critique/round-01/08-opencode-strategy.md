## 0. Verdict in six lines

1. **The owner's instinct is right, the panel's destination is right, and both overreach on timing.** "Flight recorder for Android apps" (01) is the correct 12-month category and a false claim today. The honest word now is _session_: inspect a real phone live, or replay a recorded session. That word costs nothing to claim, is runtime-neutral, and survives the companion and SDK without a second rename.
2. **The companion decision is already made by Chromium, not by the panel.** A separate APK can never attach to another app's WebView DevTools socket (verified in current `main`, §1.3). What the panel missed is the tier between "plain APK" and "shell agent": **ADB-granted development permissions** (`READ_LOGS`, `DUMP`, `PACKAGE_USAGE_STATS`, `BATTERY_STATS`, `WRITE_SECURE_SETTINGS`) persist across reboots and need no shell process. That tier is where companion v0 should live.
3. **An in-app SDK is required for any field capture of app data, and the owner already owns one.** `@cavulsqa/recorder` (JS, in the WebView, ring buffer, writes `.capu`) is the T3 seed. Generalise it; do not design a second SDK.
4. **Do not rename in the next 8 weeks.** The only moment a name becomes permanent is a Play listing (an application ID cannot change); ADB-pushed and direct-download companion builds do not create that moment. Run clearance now, rename once, at the companion's public launch.
5. **The 8-week budget should buy truth, then the visible spine, then companion v0.** Anything that needs Play review, a VPN MITM engine, JVMTI or a hosted store is a cut.
6. **Two panel facts are stale and one architecture line is wrong:** the MCP surface is 56 tools, not 30; WebView debugging is force-enabled on every `android:debuggable` build (the Chrome doc the panel cites is out of date); and a "signature-protected" binder between companion and SDK cannot work across two signing keys (§4).

## 1. My position before reading the panel

### 1.1 Category: now and in 12 months

What is true in the source, not the copy:

- **Runtime-agnostic today:** devices, apps, files, Logcat, process performance, mirror and input, native SQLite (debuggable builds only, via `run-as`: `sqlite.rs:237,351,990`), Flows, and an MCP server with **56** tools (`src-tauri/src/mcp/tools/*`, 23 of them automation and `task_*`), not the 30 the brief and inventory state.
- **WebView-bound today:** DOM, console, network, every client store (IndexedDB, OPFS, SAH-pool, jeep), framework devtools. Network is the CDP Network domain only; the product's own MCP text says native HTTP plugins are invisible (`mcp/tools/web.rs:183`); the website network card does not (`features.ts:68`).
- **Recording:** `.capu` v1 is already a cross-producer contract (`apps/docs/reference/capu-format.md:3,445-447`), with an external in-app producer and a session-store API marked "proposed, not released" (`session-store-api.md:7`, `SPEC.md:85`).
- **The "Capacitor" frame lives in four places:** the name's etymology, the runtime logo wall (`runtimes.ts`), the `capacitor` chip in the App header (`panel-05-app.png @ x438–514, y163–186`), and one client's order scenario in core types and `SPEC.md` §Automation acceptance. The website hero is already "Android WebView".

So the market-facing frame is not Capacitor; it is "WebView workbench, ten panels". That frame is a feature list, not a category. Widening it to "any Android app" would be a lie until the companion and SDK ship (release builds, native data, native HTTP are all unreachable today).

**My position:**

- **Now:** the category is _the session debugger for Android apps on real devices_. Descriptor: "Inspect a real phone live, or replay a recorded session: screen, UI, network, logs and data on one clock. Local, no account." "WebView" becomes a capability line ("deepest on apps with a web runtime"), "Android" stays a descriptor (Google's brand rules allow "for Android", not "Android X": https://developer.android.com/distribute/marketing-tools/brand-guidelines).
- **12 months:** _the flight recorder for Android apps_: always-on bounded buffer, companion in the field, SDK for release builds, a store the customer operates. Claim it only when a logcat track, a ring buffer and the companion exist.
- Why "session" and not "recorder" or "inspector" today: it is the unit the live mode, the `.capu` file, the MCP `query_recording` tools and every persona share. It makes QA, support and agents producers and consumers of the same object without turning the product into a non-developer tool.

### 1.2 Rename: whether and when

- **Whether:** yes, once, _if_ the owner commits to the broader category. The name encodes the rejected frame, and nothing outside the team knows the name yet, so the market cost is near zero. The engineering cost is real: Tauri identifier and updater continuity, the MCP server id in users' agent configs, `@capubridge/*` packages, repo URL, the `.capu` extension.
- **When:** not inside the next 8 weeks. The only irreversible moment is a public application ID (Android: "never change the application ID after publishing", https://developer.android.com/build/configure-app-module). ADB-pushed builds do not create it. Start trademark and domain clearance now; decide the name with the companion's public launch so the rename carries a story.
- **Meanwhile:** one casing in a written rule (the repo has `Capubridge`, `CapuBridge`, `capubridge` and `CAPUBRIDGE`; `SPEC.md:1,8` alone uses two), drop the "Capacitor bridge" etymology from every doc, and treat `.capu` as a format name independent of the brand, like `.har`, so a rename never touches the archive contract.

### 1.3 The companion: what a separate APK can really reach (Android 12–16, no root)

**The hard wall, verified in current Chromium `main`.** WebView's DevTools server listens on an abstract Unix socket `webview_devtools_remote_<pid>` and authorises every peer with `CanUserConnectToDevTools`, which accepts only `root`, `shell`, or a peer whose uid equals the server's own uid, and only when gid equals uid (https://chromium.googlesource.com/chromium/src/+/main/content/browser/android/devtools_auth.cc; the factory wiring in https://chromium.googlesource.com/chromium/src/+/main/android_webview/browser/aw_devtools_server.cc). A companion APK runs as its own uid, so it is refused. `sharedUserId` would need the customer's app to declare it and share the signing key; it is deprecated since API 29 (https://developer.android.com/guide/topics/manifest/manifest-element#uid). The TCP alternative (`--remote-debugging-port`) exists only when WebView reads `/data/local/tmp/webview-command-line`, which happens only on debug Android builds, not retail phones (https://chromium.googlesource.com/chromium/src/+/main/android_webview/java/src/org/chromium/android_webview/common/CommandLineUtil.java). **Nothing but root, the shell uid, or the app's own uid can attach.**

Two more platform facts that bound the design:

- Remote debugging is **force-enabled on every `android:debuggable` build** and cannot be switched off there (`SharedStatics.java`: "On debug builds, Web Contents debugging is enabled elsewhere, and cannot be disabled", https://chromium.googlesource.com/chromium/src/+/main/android_webview/glue/java/src/com/android/webview/chromium/SharedStatics.java). Chrome's own doc still says the opposite ("not affected by the debuggable flag", https://developer.chrome.com/docs/devtools/remote-debugging/webviews); the source is authoritative. Consequence: every staging build is reachable with no code change; every release build is not.
- The product already runs a **shell-uid helper**: it pushes a dex and starts `io.liriliri.aya.Server` with `app_process` as the shell user (`src-tauri/src/commands/adb.rs:64-65,499`), plus a scrcpy server. "No helper APK, no second program" (`features.ts:98,100`) is literally true and misleading.

**Therefore the SDK is required for:** any capture of DOM, console, storage or native HTTP from a **release** build; any field capture of the app's data on a phone with no developer options; writing to native databases of non-debuggable apps; crash stacks in the moment. The companion alone (tiers A+B) honestly delivers presence and consent, screen, vitals, device-wide logs and exit reasons, foreground truth, and traffic metadata. With tier C (cable-less shell uid) it delivers full CDP capture for **debuggable staging builds without an SDK**, which is the QA-on-Wi-Fi case. The owner's seed for tier D already exists: `@cavulsqa/recorder` (JS, in the WebView, 10-minute/20 MiB ring buffer, "report a problem", `capu-format.md:445-447`). It lacks only a native shim (enable debugging on demand, own-socket relay over LAN, native HTTP tap) and a framework-neutral name.

**Play policy bound (verified):** autonomous AI-driven actions through AccessibilityService are "strictly prohibited"; deterministic human-scripted automation is explicitly allowed with prominent disclosure and a declaration (https://support.google.com/googleplay/android-developer/answer/10964491). So an AI agent must act through tier C; a QA "run this Flow" through Accessibility is permissible on Play. Sideloaded (non-ADB) installs on Android 13+ hit "restricted settings" for Accessibility unless the user allows it (https://support.google.com/android/answer/12623953).

### 1.4 Personas and flows, in order

1. **Developer at the desk (live bench).** Attach → inspect → stage an edit → record. Already the product. Needs the truth layer and the request-to-row join before it is better than Chrome plus Studio on more than storage breadth.
2. **AI agent (MCP).** Second, not fifth: it is the cheapest persona to serve (56 tools exist, including durable tasks) and the most differentiated channel (`query_recording`, `read_recording_db`: evidence, not pixels). It is a channel and proof point, not a moat; and its trust surface (`shell_command`, `evaluate_js`, `confirm: true` "is not proof of human approval", `SPEC.md:91`) has not been reviewed by anyone.
3. **QA tester.** "Reproduce once, send one file." Served first by a desktop ring buffer ("save the last N minutes" removes "press Record before the bug"), then by companion v0 (tile + share), then by tier C for cable-less staging capture.
4. **Support agent.** A consumer of sessions in an evidence inbox; never a user of the bench. Needs the SDK's "report a problem" plus a share path or a customer-operated store.
5. **Field technician.** Never sees this product. Designing UI for them is waste; design the one-tap capture inside the customer's app (SDK) and the inbox on the desktop.
6. **Product people.** Read-only replay. Later.

## 2. Where I land after reading the panel

The panel's spine is sound and the red team's verification is honest. I agree with: the four S0 honesty lies as the headline; the Chromium wall as the deciding fact; "do not widen the claim before you widen the reach"; the four-tier companion design in 02; Replay landing on the library and SQLite and pid-scoped Logcat tracks on by default (03). I differ on four points:

- **The category word.** 01's "flight recorder" and 03's "field debugger" both name the 2027 product. 06's X2 says so and then leaves the word open. I close it: _session_ now, _flight recorder_ when it is true. "Field debugger" is a channel (the companion), not a category.
- **The rename window.** 01 and 06 say "before the Play listing" and imply urgency. The Play listing is Phase 3 in 02's own plan (30+ engineering weeks out). There is no urgency inside this window; there is urgency to start clearance.
- **The missing tier.** All three reports jump from "plain APK" to "shell agent". The ADB-granted development-permission tier (§1.3 B) is persistent, needs no hidden APIs, and covers the device-truth lane 02 assigns to the shell agent. Companion v0 should be built there; the shell agent then only carries what truly needs uid 2000 (CDP broker, `run-as`, injection, UiAutomation).
- **Cable-less QA without an SDK is possible for staging builds.** 03 §5 and 01 B11 treat non-developer capture as companion-plus-SDK only. Tier C over wireless debugging gives full CDP capture of debuggable builds with no cable and no SDK, at the price of developer options, a pairing code and a re-pair after reboot. That is acceptable for an internal QA team and should be the first cable-less milestone.
